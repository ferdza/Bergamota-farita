# Fixes prepared 2026-11 (OnePlus 6T), one section per item

Nothing here was run on the phone and no xnu build was done (no toolchain/CI in the authoring sandbox).
"Verified" means checked in the sandbox; "guessed" means it needs the phone. Source facts come from
`docs/reference-snippets/QCOM_CRASHDUMP.md` (Linux / downstream facts only, no GPL code copied).

## P-A. CrashDump on every reset (AUDIT_BOOT_CHAIN F-01, AUDIT_KERNEL_DRIVERS F-03/F-07/F-08)

**Problem.** The OnePlus ABL arms Qualcomm CrashDump and nothing in XNU clears it, so every reset (restart, poweroff,
a watchdog after a hung panic) is probably a CrashDump, i.e. a hard reset of the unjournaled HFS+ root. The cause is
INFERRED (symptom OBSERVED in docs/FAJITA.md).

**Fix.** `xnu/patches-11215/0272-fajita-crashdump-off-scm.patch`. On fajita only (`sweet_board_fajita()`), issue the two
SCM calls Linux `qcom_scm` and the downstream `msm-poweroff` use, as SMC64 fast calls (registers only, no locks, no
allocation): `0xC2000110` (BOOT / SET_DLOAD_MODE, args 0x10, 0) then `0xC2000109` (BOOT / SDI_CONFIG, args 1, 0).
Called at: `sweet_reboot_restart` and `sweet_reboot_poweroff` just before PS_HOLD / PSCI, and once from
`sweet_reboot_note_panic` (a hung panic that a watchdog resets must not land in CrashDump either; the panic itself
still stays up as before). Failures only log (`SWEET REBOOT: SCM crashdump off (...): dload st=N sdi st=N`), the reset
continues.
Pure logic (encodings, status decode, boot-arg parse, reset order) lives in `bsd/dev/sweet_scm_logic.h`.

**Boot-args (fajita only).**
- `sweetdload=0|1|2`: 0 = never call SCM (old behaviour), 1 = at restart/poweroff/panic (DEFAULT), 2 = also once at init.
  Mode 2 is opt-in because it puts an SMC in the boot path; the reset-time calls cannot make a boot worse.
- `sweetresetpsci=1`: restart tries PSCI SYSTEM_RESET before PS_HOLD (F-07 experiment). DEFAULT OFF: an earlier
  attempt panicked, cause unknown. The default order is byte-for-byte the old one (PS_HOLD, 2 s, PSCI, 2 s).

**Files.** `xnu/patches-11215/0272-...patch` (touches `bsd/dev/sweet_reboot.c`, adds `bsd/dev/sweet_scm_logic.h`),
`xnu/sched-test/{sweet_scm_logic.h,test_crashdump.c,run-crashdump-test.sh}`.

**F-08 correction.** The audit says poweroff writes `sr_imem[0]`; the code writes `sr_imem[SR_IMEM_RESTART / 4]`, i.e.
the restart_reason word (0x65c), an intended clear. It is left as is.

**Test.**
- Verified: the patch applies on apple_xnu-11215 after the whole series (`git apply --check`); `tools/check-patches.py`
  passes; `sh xnu/sched-test/run-crashdump-test.sh` (23 host checks, header in the patch == the tested header, built with
  `-Wall -Wextra -Werror`); the patched `sweet_reboot.c` passes `clang --target=aarch64 -fsyntax-only -Wall -Wextra`
  against stub system headers (real `sweet_board.h`/`sweet_spmi.h`); locking/context re-read: the SCM helper takes no
  lock, does not sleep and does not allocate, so it is valid in the restart path (non-preemptible, after
  `sweet_spmi_atomic()`) and in the panic path.
- Guessed (needs the phone): that the SCM clear actually cures CrashDump on the 6T (INFERRED cause), that the SMC64 SIP
  convention is what this TZ answers (the GPU zap code of patch 0103 uses it on the same SoC family), that the OnePlus
  ABL has no extra private cookie. Hardware test: boot with `sweetreboot=normal`, look for `dload st=0 sdi st=0`, then
  `reboot`: it must reach ABL / a normal boot, not CrashDump. A status of -4 means the call is unsupported: then the
  TCSR route needs an address nobody has found yet (reference pack section 7).
- Not done: Enxerto (EL1 shim) should do the same before its own PSCI reset (AUDIT_BOOT_CHAIN F-24); the 12377 series
  has no counterpart of this patch.

**Rollback.** Boot-arg `sweetdload=0` restores the old behaviour exactly; or drop patch 0272.

**Risk.** Low: a fast SCM call with a wrong id returns an error code (-4) and changes nothing; it cannot make the
reset path worse than before. Mode 2 (init) is the only variant that touches boot, and is off by default.

## P-B. Journaled HFS+ root (AUDIT_KERNEL_DRIVERS F-04, AUDIT_BOOT_CHAIN F-29)

**Problem.** The root written by `hfswrite.rs` is an unjournaled HFSX volume; hard resets leave it inconsistent (HFSINC).

**Fix (smallest safe step, host side only).** `hfswrite::Options::journal: Option<u32>` (bytes). When set, the writer does
what `newfs_hfs -J` does and nothing more: reserves one Journal Info Block (flags `InFS | NeedInit` = 0x5, offset and size
in bytes, 0xdb filler, big-endian), a contiguous journal extent after the metadata files, the two hidden root files
`.journal_info_block` / `.journal` (type `jrnl`, creator `hfs+`, invisible + name locked, UF_NODUMP), sets volume
attribute bit 13 and `journalInfoBlock` (VH byte 12), fileCount/nextCatalogID/root valence +2, and marks the blocks in the
bitmap. NO journal header is written: XNU's hfs creates it at the first writable mount (`hfs_late_journal_init` ->
`journal_create`, since lastMountedVersion is '10.0', not 'HFSJ'); the boot already mounts the root read-write
(`rootrw=1`, patch 0031). Format facts from Apple's hfs (APSL 2.0) via `docs/reference-snippets/HFS_JOURNAL.md`.
`hfsedit::apply_owners` keeps refusing journaled volumes except while the JIB still says NeedInit (nothing in the journal).

**Switch.** `renegade-rs root ... --journal 8m`, `root-ipsw ... --journal 8m`, `rootbuild::Config::journal`.
DEFAULT: unjournaled (identical bytes to before; pinned by a digest test produced with the pre-change writer).
Not exposed in the web UI or the WASM config (deliberately, until a phone has mounted one).

**Files.** `tools/renegade-rs/src/{hfswrite,hfsedit,rootbuild}.rs`, `src/bin/renegade-rs.rs`, `tests/hfsjournal.rs`.

**Test.** Verified: `cargo test --no-fail-fast` all green (5 new tests: default image digest identical to the pre-change
writer, VH/JIB/bitmap/free-count/catalog extents of a journaled image read back through renegade's own `hfs::Volume`,
size validation, edit guard); clippy shows only the pre-existing warnings. Guessed / not verified: that fsck_hfs and
XNU's hfs accept the volume (`fsck_hfs` is not available here; the layout copies newfs_hfs per the reference pack, with
the Finder flag/`jrnl` constants and the JIB offsets after byte 52 INFERRED, none of which the kernel reads), that
`journal_create` succeeds on the sweet UFS device (DKIOCGETBLOCKSIZE returns `su.secsize`, patch 0028, must be <= 4096),
and a journaled iOS boot at all.

**Failure mode to know.** If journal setup fails at a writable mount, hfs sets lastMountedVersion 'FSK!' and the mount
fails with EINVAL: the root does not mount. That is why this is opt-in: first try it on a throwaway `fastboot boot` +
userdata image, keep an unjournaled image to re-flash.

**Rollback.** Build without `--journal` (the default).
**Risk.** Zero for default builds; medium for journaled ones until a device boot proves it. Not done: the first-boot
`HFS_ENABLE_JOURNALING` route (needs the two files to exist anyway), a kernel patch to fall back to unjournaled when
journal creation fails.
