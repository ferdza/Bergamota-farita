## 0. Short answers to the three open problems

1. **Reboot ends in CrashDump, last line `unmount(0) /`.** The log line is printed by `unmount_callback` in the SECOND `vfs_unmountall(FALSE)` pass
   (vfs_subr.c:4259-4263, V); the hang is inside `dounmount(root, MNT_FORCE)`. Everything that disarms CrashDump (`sr_crashdump_off`, sweet_reboot.c:186) lives in
   `sweet_reboot_restart`, which runs only AFTER `reboot_kernel` finished (kern_shutdown.c:177-340, V). So when the unmount hangs, the SCM disarm never ran
   (default `sweetdload=1` = at reset only, 0272 `sweet_dload_mode_parse`, V), and whatever ends the hang (TZ/secure watchdog, or the user's long Power press = PMIC hard reset)
   meets an armed dload state and ends in CrashDump. Linux and the downstream driver disarm at BOOT (qcom_scm.c:2844-2850 V; downstream probe, V in QCOM_CRASHDUMP.md s.3),
   not only at reboot. Our `sweetdload=2` already does this at init; it is just not the default. **Fix = default 2 on fajita, plus read-back verification (row 1, 2).**
   Two independent bugs may be stacked: (a) disarm too late, (b) root unmount hangs. 0277 `sweetnoumount=1` addresses (b) the way Linux behaves (Linux never unmounts `/`,
   it only syncs, kernel/reboot.c:110-115 and 297-308, V; userspace remounts ro, R).
2. **IMEM `[0x1c]=0xffffffff [0x20]=0xffffffff [0xc8]=0x2016b822 [0x65c]=0xdf4e7ebf`.** None of these is a known cookie (V: downstream restart reasons are 0x77665500..0a, 0x6f656d00|NN, 0x77665501;
   dload words 0xE47B337D/0xCE14091A, EDL 0x322A4F99/0xC67E4350/0x77777777, QCOM_CRASHDUMP.md s.2). 0xffffffff at 0x1c/0x20 looks like never-written SRAM (I); 0xdf4e7ebf at 0x65c looks
   like noise, not a restart reason (I). On SDM845 the dload arming is NOT in IMEM at all (no `download_mode` node, V in QCOM_CRASHDUMP.md s.2); it is TCSR_BOOT_MISC_DETECT 0x01FD3000
   bit 0x10, set by stock firmware every boot and cleared via TZ (keyfan ArmCpu.cpp:119-122, V; Qualcomm interface header says the same register, edk2 scm_sip_interface.h:636-644, 3558-3566, V).
   So **do not chase IMEM; read TCSR through SCM IO read** (row 2). Do not write 0x1c/0xc8 (`sweetdload_imem=1` in 0274 is an experiment only; keep it off).
3. **PS_HOLD vs PSCI order.** Mainline SDM845 has NO `qcom,pshold` node (grep of sdm845.dtsi, V) so Linux restarts through PSCI SYSTEM_RESET only (psci.c:309-330, priority 129; the msm-poweroff
   PS_HOLD handler is priority 128, msm-poweroff.c:32-33, V and is not bound on this SoC). Downstream (R/V in QCOM_CRASHDUMP.md s.3) disarms SDI, then writes PS_HOLD. Siblings: PSCI only
   (edi194 0199, johnpanos/keyfan BootReset.c:96-98, flame 0098, all V). Ours: kernel PS_HOLD then PSCI after 2 s (sweet_reboot.c:356-373); Enxerto PSCI then PS_HOLD (bergamota.c:214-217). Neither order
   is proven wrong; the order matters less than (1)/(2). Linux runs it on CPU0 with other CPUs stopped (kernel/reboot.c:260,301, V); XNU runs it on whatever CPU the reboot thread has (machine_routines.c:890-900, V). See row 6.

## 3. What Linux does at reboot, in order (V, upstream master as fetched)

1. `kernel_restart_prepare` (reboot.c:110-115): reboot notifiers, then `device_shutdown()`.
2. `device_shutdown`: `qcom_scm_shutdown` (qcom_scm.c:2874-2878): download mode OFF via TCSR RMW or SCM 0x10 (row 1). `ufshcd_wl_shutdown` (ufshcd.c:10949-10978): mark shutting down, resume, quiesce, offline other LUNs,
   START STOP UNIT POWER_DOWN, link OFF, controller/regulators/clocks off; `ufs_qcom_suspend` (ufs-qcom.c:802-830) asserts the UFS reset line and waits ~10 ms.
3. `migrate_to_reboot_cpu` + `syscore_shutdown` (reboot.c:301-302), `machine_restart`, `do_kernel_restart`: highest priority handler wins, PSCI SYSTEM_RESET (psci.c:309-330) on SDM845.
4. No root unmount; no PS_HOLD write on SDM845 (no node). SDI was disabled at probe (qcom_scm.c:2849-2850), so a watchdog bite also avoids the SDI debug image.

Our equivalent today: notifiers/launchd, `sync`, forced unmount of every FS (hang), SYNCHRONIZE CACHE, PON write, optional IMEM, SCM disarm (default only here), PS_HOLD, 2 s, PSCI.

## 5. Recommended order (ideas, smallest first)

1. Default `sweetdload=2` on fajita and add the TCSR read-back + secure-write fallback + availability probe (rows 1-2); log `tcsr before/after` in `SWEET REBOOT:`. One boot tells whether the bit was set and cleared (observation, not guess).
2. Same disarm at the top of Enxerto (row 10).
3. Default `sweetnoumount=1` for `/` (row 5) and stop the syncer when shutdown starts (row 6). Add stage `printf` + `sweet_log_sync()` inside the unmount to locate the hang if it persists.
4. Bind the reset to CPU0 with IRQs masked, then evaluate PSCI-first (rows 8-9).
5. Journal the root (row 15); parse the slot suffix (row 18).

## 6. Not verified / limits

- No hardware result: every "cause" above is inference from reading; the hang location inside `dounmount` is unknown.
- The OnePlus ABL/XBL source is not available; whether ABL itself sets the dload bit is unknown (QCOM_CRASHDUMP.md s.3 also says so). edk2-porting and the `mu_platforms_oneplus6t` tree contain no dload/reboot handling for this SoC beyond the Qualcomm TZ interface header (grep, V).
- Linux UFS shutdown details and `machine_restart` CPU stop are partly R (arm64 `machine_restart` not fetched).
- SCM IO read/write IDs 0xC2000501/0xC2000502 and IS_CALL_AVAIL 0xC2000601 are V only in keyfan's source and QCOM_CRASHDUMP.md s.1, not in a Qualcomm header I read.
- `<scratchpad>/full` lacks 0274 and 0277; check that CI builds contain them before testing `sweetdload_imem`/`sweetnoumount`.
